# Consuming an aesthetic from another repo

This library is meant to be **upstream** of Timothy's other projects rather than
a workbench beside them. Bureau, Tilemakers Workshop and Doppelganger each carry
their own drifted copy of the same colours today, which is how Alyssian came to
be called Victoria in one place and how a Girando that only exists here got
rewritten from scratch in a session that could not find it.

`dist/` is what those repos read. This is the contract.

---

## The one rule: vendor it, do not fetch it

**A consuming repo copies the files it needs into its own tree and commits
them.** It does not fetch this library at runtime, and it does not fetch it at
build time either unless it already has a build.

Three reasons, and the first is decisive:

- **Bureau is an offline-first PWA.** Its whole argument is that it works on a
  phone with no signal, and a runtime fetch of another origin would put a
  network dependency inside the one app that promised not to have one.
- **An aesthetic changing should be a diff somebody reads.** Vendored, a colour
  moving shows up in a pull request in the consuming repo, next to the tiles it
  affects. Fetched, it changes under the app silently and the first anyone knows
  is that a desk looks wrong.
- **Nothing should break because Pages is down.** Three apps that stop rendering
  correctly when a fourth repo's deploy fails is a worse system than three apps
  carrying a copy.

The published copy at `https://starrysidekick.github.io/Aesthetics/dist/` exists
so the vendoring can be scripted and so a person can look. It is not an API.

---

## What is in there

Everything is generated by `node scripts/dist.mjs` from `library/*.aesthetic.json`.
**Never edit `dist/` by hand.** Edit the aesthetic and rebuild.

| File | What it is | Who wants it |
|---|---|---|
| `manifest.json` | every aesthetic's id, name, tagline, variants and content hash | a consumer deciding what to pull, or checking whether its copy has moved |
| `<id>.tokens.json` | the numbers alone, as DTCG tokens | a tool, a build step, anything that wants structured values |
| `<id>.css` | the same numbers as custom properties | a project that just wants to drop them in a stylesheet |
| `aesthetics.json` | the manifest with every token set inlined | a consumer that would rather make one request than ten |

Token names are prefixed with the aesthetic's id — `--alyssian-accent`, not
`--accent` — so two aesthetics can sit on one page and swapping between them is
swapping an attribute rather than a fight over a variable name.

## What is deliberately *not* in there

**The prose.** `library/*.aesthetic.json` carries `story`, `philosophy`, the
do/don't lists and `voice`, and those are instructions for a person or a Claude
building something in the style. An app rendering a tile has no use for them, so
the distribution is the numbers.

If you want the prose, read the aesthetic file itself, or `asGuide` in
`js/export.js`, which writes the whole thing out as a document to hand over.

**A build timestamp.** It would change on every deploy whether or not anything
did, which makes every consumer's diff noise and trains people to ignore it.

## Telling whether your copy is stale

Every aesthetic in the manifest carries a **`hash`**: the first twelve hex
characters of a SHA-256 of its token file.

```
"id": "alyssian", "hash": "ddf1343632c4"
```

Record that hash next to your vendored copy. To check for drift, fetch
`manifest.json` and compare one string per aesthetic. A hash that has not moved
means the numbers have not moved, whatever else changed in the aesthetic's prose.

This is on purpose cheaper than diffing files, and more honest than a version
number somebody has to remember to bump.

---

## Ids are the contract; your own keys are your problem

The **id** is stable and is what to key on: `alyssian`, `starprint`, `aeros`,
`golf-97`, `girando`, `stelaine`, `carca`, `fantaccio`, `hikari`.

**Your stored values are a different namespace, and mapping between them is the
consumer's job, not this library's.** Bureau stores `style: 'victoria'` in every
desk that has ever been saved, and its CSS hooks on `html[data-style="victoria"]`.
Renaming those needs a migration in Bureau and buys nothing here. So a consumer
keeps its own table:

```js
// Bureau's stored key -> the library's id. The stored key never changes;
// renaming it is a migration and this table is what makes that unnecessary.
const UPSTREAM = {
  victoria: 'alyssian',
  'starful-gothic': 'starprint',
  girando: 'girando'
};
```

Same for Tilemakers, where **Soffiando is the name of a game mode** and not a
rename of Girando the aesthetic, so there is nothing to map at all.

---

## What is stable, and what is not

`manifest.json` carries `format: "aesthetic-dist/1"`.

- **Adding a field is not a break** and does not bump the version. Read
  defensively and ignore what you do not know.
- **Moving or removing a field is a break** and bumps it to `/2`. A consumer
  should check the format string and refuse loudly rather than misread a shape
  it does not know.
- **An aesthetic's id will not change.** If one ever has to, it ships as a new
  id and the old one stays until every consumer has moved.
- **Colour values move whenever Timothy moves them.** That is the point. The
  hash is how you find out.

---

## Updating a vendored copy

1. `curl` the manifest, compare hashes against what you recorded.
2. Pull the token or CSS files whose hash moved.
3. Commit them in the consuming repo, in their own commit, with the hashes in
   the message so the next person can see what moved without re-deriving it.
4. Look at the result. These are visual apps and a colour that validates is not
   the same as a colour that works.

---

## For maintainers of this repo

`node scripts/dist.mjs` writes `dist/`. `node scripts/dist.mjs --check` verifies
the committed `dist/` still matches the library and writes nothing — it fails on
a stale file, a missing one, and a file in `dist/` that the library does not
account for. It runs in `npm test`, because a published distribution silently
drifting from the files it claims to be built from is exactly the kind of quiet
wrongness this repo keeps writing tests about.

**`dist/` is committed.** That is deliberate: it makes the vendoring diff
reviewable here as well as downstream, and it means the deploy has nothing to
compute.

This does not give the studio a build step. The studio is still a static page
served straight from the directory, with no bundler and no dependencies; `dist/`
is the existing `asCSS` and `asTokens` exports written to files instead of to a
download, and nothing in the app reads it.
